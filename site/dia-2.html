Bloco 2.2 Via Claude Code

Branches: criar e trocar

Por que não trabalhar direto na main

Tudo que você fez ontem foi direto na main, a linha principal. Isso é arriscado: se você testa uma ideia ruim ali, ela já está "oficial".

Branch resolve isso. É como duplicar um documento do Google Docs pra rascunhar uma versão nova sem tocar no original, só que, no Git, você pode ter dezenas de rascunhos ao mesmo tempo, cada um isolado, e decidir depois quais voltam pro documento principal.

O que é fazer switch

É trocar qual rascunho está aberto na sua pasta local.

💡 E aqui vem a parte que costuma surpreender: quando você troca de branch, os arquivos na sua pasta mudam de conteúdo na hora, como se alguém trocasse os papéis da sua mesa enquanto você não olhava. Ontem isso seria impossível de ver, porque você não tinha pasta local. Hoje tem.

Exercício

06 Criando uma branch e vendo a pasta local mudar

O cenário: o time de marketing quer testar uma paleta de cores diferente pro slide de capa, sem arriscar a versão que já está no ar.

Entregável: uma branch variacao-cores com uma versão diferente do slide de capa, commitada e publicada, e a experiência de ver a pasta local mudar de conteúdo ao trocar de branch.

Passo 1

Crie a branch

Prompt 1

Cria uma branch chamada variacao-cores a partir da main e muda pra ela. Depois me confirma em qual branch eu estou.

Passo 2

Peça a mudança de cor, na branch nova

Prompt 2

Nessa branch, muda a paleta de cores do slide de capa do index.html pra tons de verde e roxo, mantendo a estrutura e os textos iguais.

Abra o index.html da pasta no navegador e confirme que a cor mudou. Se não gostou, peça um ajuste antes de commitar, está tudo isolado nesta branch.

Passo 3

Commite e publique a branch

Prompt 3

Commita com a mensagem "testando paleta verde e roxo" e faz push desta branch.

Vá no github.com, na aba Branches do seu repositório: agora existem duas. A main e a variacao-cores.

Passo 4

Volte pra main e veja o arquivo mudar sozinho

Antes de pedir, deixe o index.html aberto no navegador, numa aba visível. Depois:

Prompt 4

Volta pra branch main.

Agora recarregue aquela aba do navegador. A cor voltou pro azul e branco.

Você não editou nada, e o Claude Code não reescreveu o arquivo. O arquivo na sua pasta mudou de conteúdo sozinho, só porque a branch ativa mudou.

💡 Peça "volta pra variacao-cores" e recarregue de novo. Vai e volta quantas vezes quiser: é o mesmo arquivo, no mesmo caminho, com dois conteúdos possíveis.

O que fixar

A branch não é uma pasta separada: é a mesma pasta mudando de estado conforme a linha do tempo ativa. É isso que permite ter dezenas de variações sem duplicar pasta nenhuma.

Bônus · opcional

O que o Claude Code roda por trás

Nada depois disso depende deste bônus. O objetivo é reconhecimento, não decoreba, mas é o que transforma "ele fez alguma coisa" em "eu sei o que ele fez".

Cada pedido que você faz em português vira um comando de Git. Você não precisa digitá-los, mas reconhecer ajuda muito, porque é a língua que qualquer tutorial, post de blog e mensagem de erro falam.

O que você pediuO que ele rodou
"me mostra o histórico"git log --oneline
"tem mudança pendente?"git status e git diff
"cria uma branch e muda pra ela"git checkout -b variacao-cores
"volta pra main"git checkout main
"commita com a mensagem X"git add . + git commit -m "X"
"faz push desta branch"git push -u origin variacao-cores

Exercício

B Confira na unha o que ele fez

A ideia é ver, em texto e por conta própria, o mesmo estado que o Claude Code te contou em português. Nada aqui muda o seu repositório.

Entregável: nenhum arquivo.

Passo único

Saia do Claude Code e rode você mesmo

  1. Saia do Claude Code (Ctrl + C ou digitando /exit), você volta pro terminal comum, na mesma pasta
  2. Rode git log --oneline e compare com o histórico que ele te descreveu
  3. Rode git branch. As duas branches aparecem, e a que tem * na frente é a ativa, a mesma que ele disse que estava
  4. Rode git status. Sem mudanças pendentes, ele responde nothing to commit, working tree clean
  5. Rode claude de novo pra voltar

💡 Você acabou de auditar o trabalho dele. É exatamente isso que dá pra fazer quando alguém, pessoa ou máquina, mexe num repositório seu: o Git registra tudo, e o registro é público pra quem tem acesso.

O que fixar

O Claude Code não faz nada de mágico nem de invisível. Ele roda os mesmos comandos que estariam ali de qualquer jeito, e deixa rastro, do mesmo jeito que você deixaria.

Bloco 2.3 Em dupla · a partir daqui

Formem a dupla

Todo o resto do dia é em dupla, num repositório que vocês dois vão criar juntos. Escolham quem é a pessoa A e quem é a pessoa B: os exercícios usam esses nomes pra dizer quem faz o quê.

Até agora o repositório era seu e ninguém mais mexia nele. Num projeto de verdade não é assim: várias pessoas trabalham no mesmo código, ao mesmo tempo, sem combinar cada linha.

É justamente aí que branch, merge e Pull Request deixam de ser burocracia e viram a única forma de isso não virar bagunça.

Exercício

07 Um repositório para os dois

Vocês vão criar um repositório novo, dar acesso um ao outro e clonar os dois na mesma base. Do fim deste exercício em diante, os dois computadores apontam pro mesmo projeto.

Entregável: um repositório novo e público, com os dois como colaboradores, clonado nas duas máquinas e com o Pages ligado.

Passo 1

Pessoa A cria o repositório e o primeiro slide

Só a pessoa A faz este passo. No Claude Code, numa pasta fácil de achar:

Prompt 1 · pessoa A

Cria um repositório público novo no GitHub chamado prototipo-dupla-<nomes de vocês>, clona ele aqui e coloca dentro um index.html com um slide de capa da campanha "Indique um amigo e ganhe R$ 50" da ArenaCash. O slide precisa ter um botão com o texto "Saiba mais". Commita e faz push.

💡 O botão importa: é nele que o conflito do próximo bloco vai acontecer. Confirme que ele existe antes de seguir.

Passo 2

Pessoa A dá acesso à pessoa B

No navegador, no repositório novo:

  1. Settings → no menu lateral, Collaborators
  2. Clique em Add people
  3. Digite o usuário do GitHub da pessoa B e confirme

Pessoa B: você recebe um convite por email e também em github.com/notifications. Aceite antes de seguir, senão o clone do próximo passo falha.

Passo 3

Pessoa B clona, e os dois ligam o Pages

Prompt 2 · pessoa B

Clona o repositório <usuario-da-pessoa-A>/prototipo-dupla-<nomes> aqui nesta pasta e me mostra o que tem dentro.

Pessoa B: abra o index.html local no navegador e confirme que vê o mesmo slide que a pessoa A vê. Agora existem três cópias do projeto: a da máquina de A, a da máquina de B e a do GitHub.

Pra fechar, pessoa A liga o GitHub Pages neste repositório novo, do mesmo jeito que vocês fizeram no repositório de cada um ontem, no Bloco 1.5 do Dia 1: Settings → Pages → Branch main → / (root) → Save. Guardem a URL: é ela que vai mostrar o resultado do trabalho de vocês dois.

O que fixar

Adicionar colaborador é o que transforma um repositório pessoal em projeto de time. A partir daqui, tudo que um dos dois manda pro GitHub, o outro consegue puxar. E é essa possibilidade que cria o conflito do próximo bloco.

Bloco 2.4 Em dupla · decisão de vocês

O conflito de verdade

É o bloco mais denso do dia. Vocês dois vão mudar a mesma linha ao mesmo tempo, sem combinar o texto, e depois resolver o que o Git não consegue resolver sozinho.

Merge é o cruzamento

Uma branch só tem valor se, em algum momento, ela volta pra se juntar com a principal. Isso se chama merge.

Quando dá certo

As mudanças estão em partes diferentes do arquivo. O Git junta sozinho, sem perguntar nada.

Quando dá conflito

Duas pessoas mudaram a mesma linha de formas diferentes. O Git não tem como adivinhar quem está certo.

💡 Conflito é o Git sendo honesto: duas pessoas mudaram a mesma coisa, e ele não vai escolher por vocês. Quem escolhe são vocês, não o Claude Code.

O que vai acontecer, passo a passo

Este desenho acompanha o Exercício 8. Conforme vocês marcam os passos abaixo, ele se redesenha pra mostrar onde vocês estão.

Exercício

08 Causem um conflito e resolvam juntos

A regra do exercício: não combinem o texto do botão. Cada um escolhe o seu, sem contar pro outro. O conflito precisa ser real pra valer a pena.

Entregável: um conflito de verdade, causado pelos dois, resolvido com um texto que vocês decidiram juntos e mesclado na main.

Passo 1

Os dois, ao mesmo tempo: cada um na sua branch

Façam este passo simultaneamente, cada um no seu computador. Não olhem a tela do outro.

Prompt 1 · pessoa A

Cria uma branch chamada botao-a a partir da main. Nela, troca o texto do botão do index.html por [escolha um texto e não conte pra sua dupla]. Commita com a mensagem "novo texto do botao" e faz push.

Prompt 2 · pessoa B

Cria uma branch chamada botao-b a partir da main. Nela, troca o texto do botão do index.html por [escolha um texto e não conte pra sua dupla]. Commita com a mensagem "novo texto do botao" e faz push.

Abram a aba Branches do repositório no github.com. As duas branches estão lá, lado a lado, cada uma com o texto que só quem a criou conhece.

Passo 2

Pessoa A mescla primeiro

Prompt 3 · pessoa A

Vai pra main, mescla a branch botao-a nela e faz push.

Entrou liso, sem conflito nenhum. Quando a pessoa A começou, a main ainda era a original, e ninguém tinha tocado naquela linha.

💡 Pessoa B: abra a URL pública da dupla agora. O botão já mostra o texto que a pessoa A escolheu, e você não fez nada. O trabalho dela chegou até o ar sem passar por você.

Passo 3

Pessoa B tenta mesclar e o Git trava

Prompt 4 · pessoa B

Puxa a main atualizada do GitHub e tenta mesclar a minha branch botao-b nela. Se der conflito, não resolve sozinho: me mostra o trecho em conflito, com os marcadores, e me explica o que cada lado quer.

Agora trava. O Claude Code vai mostrar algo assim:

<<<<<<< HEAD
<button>[o texto que a pessoa A escolheu]</button>
=======
<button>[o texto que a pessoa B escolheu]</button>
>>>>>>> botao-b

Entre <<<<<<< HEAD e ======= está o que já está na main, ou seja, a versão da pessoa A. Depois do ======= está a versão da pessoa B.

💡 Repararam por que ele travou agora e não no passo anterior? Porque a main mudou depois que a pessoa B começou a trabalhar. É esse descompasso que produz conflito, e é por isso que ele aparece muito mais em time do que sozinho.

Passo 4

Decidam juntos e finalizem

Agora conversem. Vocês têm dois textos na tela e precisam sair com um. Fica o da pessoa A, o da pessoa B, ou um terceiro que junte os dois?

Se quiserem uma opinião antes de decidir:

Prompt 5 · opcional

Sem aplicar nada ainda: qual dos dois textos funciona melhor pro botão de uma campanha de indicação, e por quê?

Com a decisão tomada:

Prompt 6 · pessoa B

Resolve o conflito deixando o texto do botão como [o texto que vocês decidiram], apaga os marcadores, finaliza o merge e faz push.

Pessoa A: peça ao Claude Code pra puxar a main atualizada e abra o index.html. O texto que aparece é o que vocês combinaram, e ele chegou na sua máquina sem você ter editado nada.

O que fixar

Resolver conflito é olhar as duas versões, decidir qual fica e seguir. O Git só precisa que uma pessoa decida.

O que ele fez de útil aqui foi impedir que o trabalho de um sobrescrevesse o do outro em silêncio. Sem Git, quem salvasse por último ganhava, e ninguém ficaria sabendo.

Bloco 2.5 Em dupla

Pull Request: revisar antes de aprovar

No exercício anterior vocês mesclaram direto. Funciona, mas ninguém olhou o trabalho do outro antes de virar oficial. O Pull Request é onde essa conversa acontece.

Um PR é um pedido de "quero juntar minha branch na main, você olha antes?". Ele vive no github.com e permite três coisas:

Ver o diff

O que exatamente mudou, linha por linha. A mesma tela que você viu ontem, no Bloco 1.4.

Comentar

Em linhas específicas, não só no geral.

Aprovar

Ou pedir mudanças antes de aceitar.

💡 É como mandar um Loom de aprovação, só que pra código, ou no nosso caso pra HTML.

Exercício

09 Um PR de cada, revisado pelo outro

Cada um abre um Pull Request com um slide novo, e revisa o do colega antes de aprovar. Ninguém mescla o próprio PR sem passar pelo outro.

Entregável: dois PRs, cada um com pelo menos um comentário do colega, aprovados e mesclados na main.

Passo 1

Cada um cria o seu slide e abre o PR

Dividam: a pessoa A faz o slide de benefícios, a pessoa B faz o slide de depoimento. Cada um no seu computador, ao mesmo tempo.

Prompt 1 · pessoa A

Cria a branch slide-beneficios a partir da main. Nela, adiciona ao index.html um slide listando 3 benefícios da campanha: R$ 50 pro indicado, R$ 50 pra quem indicou, sem limite de indicações. Mantém o visual consistente. Commita, faz push e abre um Pull Request pra main. Me devolve o link.

Prompt 2 · pessoa B

Cria a branch slide-depoimento a partir da main. Nela, adiciona ao index.html um slide com um depoimento fictício de um cliente da ArenaCash sobre a campanha, com nome e uma citação curta. Mantém o visual consistente. Commita, faz push e abre um Pull Request pra main. Me devolve o link.

Passo 2

Revisem o PR um do outro

Troquem os links. Esta parte é no github.com mesmo: revisão é conversa entre pessoas, não tarefa pra automatizar.

  1. Abra o PR do colega e clique na aba Files changed
  2. Veja o diff, com o que foi adicionado em verde
  3. Passe o mouse numa linha e clique no +. Deixe um comentário de verdade, algo que você mudaria
  4. Clique em Review changes → Approve
Passo 3

Respondam, mesclem e vejam o segundo dar trabalho

Cada um lê o comentário que recebeu e, se fizer sentido, ajusta:

Prompt 3 · se for ajustar

Na minha branch, [descreva o ajuste que o colega pediu]. Commita e faz push. O PR deve atualizar sozinho.

Agora mesclem, um de cada vez: primeiro o PR da pessoa A, depois o da B.

💡 O segundo PR pode acusar que precisa atualizar antes de mesclar, porque a main andou. Se acontecer, peça ao Claude Code: "puxa a main atualizada pra dentro da minha branch e resolve o que precisar". É o mesmo mecanismo do bloco anterior, agora numa situação rotineira.

O que fixar

O PR é o momento onde a conversa acontece antes de a mudança virar oficial. Em produto real, quem revisa costuma ser o tech lead ou o par de design. O mecanismo é exatamente esse.

Bloco 2.6 Em dupla

Claude Code lendo código: documentar o algoritmo

Até aqui vocês usaram o Claude Code pra criar e mexer. Ele também lê e explica, e é isso que responde a pergunta que ficou em aberto no Dia 1: quanto tempo você levaria pra entender aquele algoritmo com ele do lado.

Exercício

10 Documentem o algoritmo da ArenaCash

Lembram do Exercício 2 do Dia 1? Vocês garimparam o simulador.js na mão. Agora refazem aquilo em três pedidos, e saem com um documento pronto pra mandar pra alguém.

Entregável: um analise-simulador.md commitado no repositório da dupla. Pessoa B conduz o Claude Code; pessoa A lê e questiona.

Passo 1

Peçam a explicação e comparem com a de ontem

Prompt 1

Lê o arquivo simulador.js do repositório público github.com/Product-Arena/arena-cash e me explica, em português e sem jargão, como ele decide qual investimento indicar pra cada pessoa.

💡 Comparem a resposta com o que vocês descobriram ontem lendo o arquivo na mão. Bateu? Ele achou algo que passou despercebido? Disse algo que vocês sabem que está errado?

Passo 2

Peçam o que é difícil achar sozinho

Prompt 2

Quais regras desse arquivo podem gerar um resultado que surpreende o cliente? Pra cada uma, me dá um exemplo concreto de idade, salário e perfil que cai nela, e explica por que o resultado parece contraditório.

Ele deve encontrar pelo menos duas: a do aporte mínimo, que passa por cima do perfil e da idade, e a do teto de risco por idade.

⚠️ Pessoa A, este passo é seu: se ele apontar algo que vocês não conseguem confirmar no código, não aceitem. Peçam "me mostra a linha exata do arquivo onde isso acontece".

Passo 3

Peçam o material detalhado e commitem

Prompt 3

Cria um arquivo analise-simulador.md aqui no nosso repositório documentando esse algoritmo, com estas seções:

1. O que o simulador faz, em um parágrafo
2. Tabela dos produtos, com rendimento, prazo e risco
3. Como a pontuação é calculada, passo a passo
4. As regras que têm precedência sobre a pontuação
5. Casos-limite, com exemplos de idade, salário e perfil
6. Perguntas que eu levaria pro time de produto sobre essas regras

Escreve pra alguém que não sabe programar. Sem jargão.

Leiam antes de aceitar. É o documento de vocês: se alguma seção ficou rasa, peçam pra refazer só aquela. Quando estiver bom, commitem e façam push.

O que fixar

Ontem vocês levaram doze minutos garimpando um arquivo pra entender duas regras. Hoje levaram três pedidos, e saíram com um documento.

Mas vocês só conseguem julgar se a resposta está certa porque já tinham feito na mão. Quem pula a etapa de ontem recebe o mesmo documento e não tem como saber se pode confiar nele.

Bloco 2.7 Em dupla · o desafio

Desafio final: dois construindo ao mesmo tempo

O exercício que junta tudo. Vocês vão construir duas funcionalidades novas em paralelo, no mesmo repositório, sem parar pra esperar um pelo outro.

A regra que faz o exercício valer

Escolham duas funcionalidades que ainda não existem no protótipo de vocês, uma pra cada. Depois trabalhem ao mesmo tempo, cada um na sua branch, sem combinar como cada um vai fazer.

Esperar o outro terminar seria mais fácil, e é exatamente por isso que não vale. O ponto do dia é conseguir avançar em paralelo e juntar depois.

Se precisarem de inspiração

FAQ

Um slide com 2 ou 3 perguntas frequentes sobre a campanha.

Números

Uma seção de prova social, tipo "10.000 indicações já feitas".

Compartilhar

Um botão de compartilhar no WhatsApp.

Navegação

Setas ou teclado pra passar de slide.

Exercício

11 Duas funcionalidades, dois autores, um site no ar

Ciclo completo, sem roteiro passo a passo: vocês já fizeram cada peça hoje. Agora é juntar todas, em paralelo, e publicar.

Entregável: o site da dupla no ar, com as duas funcionalidades novas, cada uma tendo passado por um Pull Request revisado pelo outro.

Passo 1

Combinem só o "o quê", nunca o "como"

  1. Escolham as duas funcionalidades e escrevam num papel quem faz qual
  2. Combinem também onde cada uma entra no index.html. Se as duas forem mexer no mesmo lugar, o conflito é garantido
  3. Cada um cria a sua branch, com um nome que descreva a ideia

💡 Este passo de combinação é a única coisa que separa "trabalho em paralelo" de "os dois reescrevendo o mesmo pedaço". Em time de verdade, é a mesma conversa.

Passo 2

Construam ao mesmo tempo

Cada um pede a sua funcionalidade ao Claude Code, na sua branch. Sem esperar o outro.

  1. Descreva a funcionalidade que você quer no index.html
  2. Abra o arquivo local no navegador e confira antes de continuar
  3. Peça commit, push e abertura de um Pull Request
Passo 3

Revisem, mesclem os dois e resolvam o que aparecer

  1. Revisem o PR um do outro no github.com, com pelo menos um comentário
  2. Mesclem o primeiro PR
  3. Mesclem o segundo. Se ele reclamar que a main andou, peça ao Claude Code: "puxa a main atualizada pra dentro da minha branch e resolve o que precisar"

Se aparecer conflito aqui, vocês já sabem o que fazer: olhar as duas versões, decidir juntos e finalizar.

Passo 4

Confiram no ar e mostrem pro grupo

Prompt · qualquer um dos dois

Confirma que o GitHub Pages já está servindo a versão nova e me devolve a URL pública.

Abram a URL numa aba anônima. As duas funcionalidades estão lá, construídas em paralelo, por duas pessoas, sem ninguém sobrescrever o trabalho do outro.

Compartilhem o link e contem pro grupo o que cada um fez e se deu conflito no caminho.

O que fixar

Isso é um time de produto trabalhando. Duas pessoas, um repositório, mudanças em paralelo, revisão antes de aprovar e uma URL que se atualiza sozinha a cada merge.

A diferença entre isso e o trabalho de vocês na segunda-feira é o assunto, não o mecanismo.
